# Prior art: a watch list

Research note, not a decision document. Scope: sunscatter targets N-body gravity everywhere (no SOIs), warp to 1e5-5e5x with bit-identical outcomes at every warp setting, 5,000-part craft, lumped-network subsystem simulation (fluids/power/thermal/data as node-link graphs), and generic part types that compose into any real vehicle (scope-2026-11.md, sections 2-3). This note lists who else is building toward some piece of that, what to learn from each, and where sunscatter has to be stronger. Status tags: **confirmed** (developer statement, docs, or direct observation) vs **rumoured** (forum/community inference, unconfirmed).

1. Kitten Space Agency (in depth)
2. Shorter entries: the realism stack, KSP2, Orbiter, Juno/SR2, CoaDE, Space Engineers, Spaceflight Simulator, Reentry, Flight of Nova, NASA tools
3. Comparison table
4. Ideas to steal / traps to avoid

## 1. Kitten Space Agency (KSA)

**What it is.** A spaceflight sandbox from RocketWerkz (Dean Hall, creator of DayZ; team includes KSP/KSP2 veterans HarvesteR, Blackrack and JPLRepo, plus former KSP modders, and an ex-SpaceX engineer), explicitly pitched as the spiritual successor to Kerbal Space Program after KSP2's collapse. Announced October 2024, pre-alpha launched free in November 2025, distributed only through RocketWerkz's own Ahwoo platform (not Steam/EGS). No price, no roadmap, no beta or 1.0 date; development is funded by voluntary contributions, with a possible move to paid later ([space.com interview](https://www.space.com/entertainment/space-games/kitten-space-agency-is-the-spiritual-successor-to-kerbal-space-program-and-they-have-an-ex-spacex-engineer-on-the-team-interview), [RocketWerkz wiki](https://en.wikipedia.org/wiki/RocketWerkz), [KSA wiki.gg](https://kittenspaceagency.wiki.gg/wiki/Kitten_Space_Agency), [FAQ](https://kittenspaceagency.wiki.gg/wiki/Frequently_asked_questions)). Status as of Nov 2026: active weekly/monthly builds (e.g. build 5707, "2026.8.22"), still pre-alpha ([version history](https://kittenspaceagency.wiki.gg/wiki/Version_history)).

**Engine and tech — confirmed.** Custom in-house engine, "BRUTAL", built because Dean Hall was frustrated with Unity/Unreal for this kind of simulation; BRUTAL has since been open-sourced ([Dean Hall on X](https://x.com/rocket2guns/status/1942222168085205338)). Physics runs on **Bepu** (a C#-native physics library), rendering is a **Forward+ pipeline with clustered shading**, and positions use 64-bit double precision with the camera kept near the origin to control floating-point error at interplanetary scale ([FAQ](https://kittenspaceagency.wiki.gg/wiki/Frequently_asked_questions)). The modding story ("C# injection") implies the gameplay/sim layer is C#, consistent with Bepu and with the KSP1 lineage of the team. Multiplayer networking reuses RocketWerkz's own RakNet-derived stack ("RocketNet") from Stationeers, said to be orders of magnitude more scalable than off-the-shelf nets ([search summary citing dev interview](https://nichegamer.com/dayz-creator-reveals-kerbal-space-killer-game-kitten-space-agency/)). Windows is the only officially supported platform; Linux is experimental, macOS is not planned.

**Orbital/physics model.** **Confirmed**: patched conics, not N-body, is the core orbital model for the base game — the FAQ states this directly ("the game will use patched conics for orbital simulation; n-body simulation is not planned to be implemented as part of the base game") ([FAQ](https://kittenspaceagency.wiki.gg/wiki/Frequently_asked_questions), [Planned features](https://kittenspaceagency.wiki.gg/wiki/Planned_features)). **Rumoured/contested**: some community summaries describe N-body as merely "disconfirmed for official inclusion... but potentially feasible through community mods," and a third tracker (Are We KSA Yet) lists N-body status as flatly "no info yet" ([areweksayet.com](https://areweksayet.com/)). Treat "patched conics, N-body only via mods, if ever" as the working assumption — this is the single biggest fidelity gap between KSA and sunscatter's no-SOI N-body requirement.

**Part/vessel model — confirmed.** 6-DOF rigid body physics with collision, basic drag, buoyancy and thrust is in; structural failure is driven by impact, g-limit and dynamic-pressure thresholds, producing trackable, saved debris; parts show visible dents from impact damage. Max parts per vessel is capped at 65,535 (`ushort.MaxValue`), with GPU instancing and a "subparts" system meant to make large craft affordable; actual performance at high part counts is undocumented pre-beta ([FAQ](https://kittenspaceagency.wiki.gg/wiki/Frequently_asked_questions), [Are We KSA Yet](https://areweksayet.com/)). Staging, gimbal/vectoring, RCS, multiple liquid engines, configurable-grain solid boosters and vernier-integrated mains are functional.

**Aero, thermal, fuel flow, multi-vessel — confirmed gaps.** Aerodynamics is currently a **per-axis bounding-box drag area** keyed to vehicle orientation, with no lift model, no aero stability analysis, and atmospheric density only affecting engine performance — explicitly WIP. **Thermal is not implemented at all**: no heat shield, no reentry heating. **Multi-vessel physics/interaction beyond docking is not implemented.** Communications (line-of-sight, signal strength, data) are absent. Parachutes are relatively advanced (reefing, line stretch, burst pressure, cloth sim up to 30x warp, visual only) ([Are We KSA Yet](https://areweksayet.com/)). No published fuel-flow/plumbing network model was found; current propulsion appears to be per-part, not a routed fluid network.

**Time warp and determinism.** Time warp goes up to 100 years/second claimed, but community bug reports describe severe frame-rate collapse (down to <1 fps) when warping while actively piloting a vessel, tied to effects (e.g. particle FX) that don't scale off with warp ([ahwoo forums bug report](https://forums.ahwoo.com/forums/kitten-space-agency/bug-reports/severe-fps-drop-down-to-1-fps-lag-at-high-time-warp-due-to-launch-particle-fx-scaling-with-simulation-speed.976/), [laggy time warp thread](https://forums.ahwoo.com/forums/kitten-space-agency/bug-reports/the-timewarp-is-really-laggy.932/)). Physics is stated to run decoupled from rendering so off-screen/unfocused vessels keep simulating regardless of warp or frame rate — a necessary condition for determinism, but no developer statement claims bit-identical outcomes across warp levels, and no test suite or methodology for that claim is published. This is the second major gap versus sunscatter: KSA is aiming for "warp feels right," not "warp is provably invariant."

**Modding.** Strong, deliberate story: "the core game data itself is a mod," so changing planets/systems, injecting C#, and customizing shaders are all first-class, officially-supported paths, distributed via SpaceDock and a Borea content manager, with a dedicated modding Discord ([SpaceDock mods](https://spacedock.info/ksa), [Planned features](https://kittenspaceagency.wiki.gg/wiki/Planned_features)). A formal scripting framework/API is explicitly **not yet implemented** — an open gap relative to sunscatter's planned AI-interface parity with the UI.

**Design philosophy and reception.** Dean Hall frames KSA as built to recapture "the feeling, commitment and challenge" of original KSP after KSP2's failure, with "some tech firsts" and a commitment to building a custom engine rather than reusing Unity ([X post](https://x.com/rocket2guns/status/1942222168085205338)). Community sentiment is mixed-to-cautiously-optimistic: skepticism from Hall's track record (DayZ's long early access) coexists with credibility from hiring original KSP/KSP2 engineers and modders ([search synthesis](https://nichegamer.com/dayz-creator-reveals-kerbal-space-killer-game-kitten-space-agency/)); no systematic fidelity review was found as of Nov 2026, consistent with the project still being pre-alpha with large unimplemented systems (thermal, aero lift, N-body, comms).

**Bottom line for sunscatter.** KSA is the nearest commercial-mindshare competitor and worth tracking closely for UX, modding culture and engine-building lessons, but its *confirmed* physics core (patched conics, no thermal, box-drag aero, no fluid network, warp without a determinism proof) sits well below sunscatter's target. Sunscatter's edge has to be N-body everywhere, a real lumped-network solver for fluids/thermal/power, and warp invariance as a tested, provable property, not a feel.

## 2. Shorter entries

### KSP 1 + Principia + RSS/RO/RP-1 (the realism stack)
KSP1 itself uses patched conics and per-body SOIs with a single fixed physics step; its realism comes entirely from a mod stack layered on top. **Principia** (MIT-licensed, open source, [github.com/mockingbirdnest/Principia](https://github.com/mockingbirdnest/Principia)) replaces stock integration with a true n-body/extended-body gravitation model (every vessel is pulled by every celestial, not just the one it's "inside"), using a higher-order symplectic integrator, with predictions computed asynchronously so long-range forecasts near complex gravity fields (Earth-Moon under RSS) stay usable. **Real Solar System (RSS)** swaps in real celestial bodies and distances; **Realism Overhaul (RO)** reconfigures stock and modded parts to real engines/tanks/avionics; **RP-1** layers a career/progression mode on top of RSS+RO ([KSP-RO org](https://github.com/ksp-ro), [RP-1](https://github.com/KSP-RO/RP-1)). What to learn: Principia proves that full n-body plus patched-conics UI (maneuver nodes, transfer planner) can coexist, and that a correct physics core can be bolted onto a game never designed for it. Limits sunscatter must exceed: Principia is still a bolt-on running inside KSP1's single-threaded, single-rate loop — no warp-invariance guarantee, no lumped-network subsystems (fuel is still simple tanks), no determinism across machines was ever a design goal, and the whole stack depends on an increasingly unmaintained 2011-era game engine.

### KSP 2 (what failed and why)
Take-Two split Star Theory's staff to form a new in-house studio (Intercept Games) mid-development, which both destabilized the original studio and gutted Intercept's own headcount at launch; management reportedly forced reuse of KSP1's aging codebase instead of a clean rebuild, undercutting the ambitious scope (multiplayer, interstellar travel, colonies) the creative director had pitched. Early access released at $49.99 with orbital mechanics and reentry barely functional and severe performance/physics bugs, after marketing had implied more progress than existed. Take-Two shut Intercept down in May 2024 ([gamedesignskills postmortem](https://gamedesignskills.com/game-design/why-did-kerbal-space-program-2-fail/), [techdriveplay retrospective](https://techdriveplay.com/2025/01/03/kerbal-space-program-2-a-tale-of-corporate-neglect-and-failure/)). Lesson for sunscatter: scope and budget must be matched before public commitments are made, and a "rebuild on the old foundation under time pressure" plan is a known failure mode — directly relevant to this project's own warning against pacing to a deadline.

### Orbiter 2016 (and its open-source continuation)
Martin Schweiger's Orbiter is a free Newtonian spaceflight simulator (patched N-body-capable gravity for major bodies, double-precision state vectors, accurate ephemerides) long used as a semi-serious engineering/teaching tool. The original 2016 release's source was published and is now maintained as a community open-source project under MIT license ([github.com/orbitersim/orbiter](https://github.com/orbitersim/orbiter), active commits as of Nov 2026), with several community forks. What to learn: Orbiter proved a hobby-scale team can deliver believable multi-body gravity, accurate ephemerides and a serious addon/vessel-API ecosystem (DeltaGlider, Shuttle Fleet, etc.) that outlived the original studio once opened up. Limits sunscatter must exceed: no lumped-network subsystems (fuel, power and thermal are script-level approximations per addon, not a shared solver), no part-level structural failure, no time-warp-with-invariance concept at all (its "time acceleration" simply scales the step, with no determinism guarantee), and a 2000s-era single-threaded architecture that caps craft complexity and scene scale.

### Juno: New Origins / SimpleRockets 2
A mobile-first-to-desktop rocket/plane sandbox (Steam: [store.steampowered.com/app/870200](https://store.steampowered.com/app/870200/Juno_New_Origins/)) with real orbital mechanics and a unified part system that builds rockets, planes, and ground vehicles from the same procedural parts. Designed to run on phones, so official guidance caps part counts around 280-400 for playable performance — orders of magnitude below sunscatter's 5,000-part target. What to learn: a genuinely unified, procedural part system (not discrete catalog parts) that spans multiple vehicle classes without special-casing. Limits to exceed: no n-body, no thermal/aero fidelity beyond simplified drag, no lumped subsystem network, and part-count ceilings baked in by the mobile-performance design goal.

### Children of a Dead Earth (CoaDE)
A 2016 orbital warfare simulator built as "a realistic material science and orbital simulator first, game second": true n-body gravitation (the kind used for real trajectory work), correctly modelled hyperbolic orbits, Lagrange points and perturbations, and weapons/propulsion (railguns, thermal rockets, plasma thrusters) implemented from textbook physics formulas rather than balanced game stats ([TV Tropes summary](https://tvtropes.org/pmwiki/pmwiki.php/VideoGame/ChildrenOfADeadEarth), [orbiter-forum thread](https://www.orbiter-forum.com/threads/children-of-a-dead-earth.35700/)). What to learn: CoaDE is the strongest existing proof that n-body-correct, first-principles part physics can ship as a real (if niche) game, and that combat/mission design can be built honestly on top of orbital mechanics rather than around it. Limits to exceed: single-player, single-scenario scale (no persistent campaign, no multi-vessel warp economy), no subsystem network beyond heat/propellant bookkeeping per craft, no time-warp-at-scale story at all — matches are short and real-time-ish by design.

### Space Engineers (structure/damage)
Keen Software House's voxel-and-grid sandbox models ships and stations as block grids with per-block hitpoints and component-level integrity; blocks visibly deform and lose function progressively before outright destruction, explosions carve voxel terrain and can be partially shielded by intervening blocks/grids, and un-finished (under-construction) blocks carry correct mass but deal no impact damage ([Damage Mechanics wiki](https://spaceengineers.wiki.gg/wiki/Damage_Mechanics)). What to learn: a believable, readable progressive-damage model (deform → lose function → destroy) built from simple per-block state, which is close to sunscatter's own ring-of-cells failure proposal. Limits to exceed: no orbital mechanics worth the name (flat/simplified gravity wells, no n-body), no real thermal or fluid network, and voxel-terrain damage is a memory/perf liability at scale that sunscatter's cell-based structural model must avoid inheriting.

### Spaceflight Simulator
A free-to-play mobile/PC 2D rocket sandbox with real-ish Newtonian gravity and a large casual audience; focuses on accessible rocket building and simple multi-body gravity wells rather than fidelity. What to learn: extremely low-friction onboarding and a UI that makes orbital mechanics intuitive to total beginners — relevant to sunscatter's "equal weight" game/tool duality. Limits to exceed: 2D, no subsystem simulation, no structural/thermal/aero modelling beyond cosmetic, and no claim to professional credibility.

### Reentry: An Orbital Simulator
A hard-accuracy recreation of Mercury, Gemini and Apollo flight procedures and spacecraft computers, aiming to fly the exact checklists and switch sequences used in the 1960s ([orbiter-forum thread](https://www.orbiter-forum.com/threads/reentry-an-orbital-simulator.36802/)). Known rough edges include inaccurate state vectors and glitchy docking (reported ~20 cm position jumps rather than smooth approach) that required a dedicated rendezvous/docking rewrite ([Steam discussion](https://steamcommunity.com/app/882140/discussions/0/3047182953366126267/)). What to learn: procedure-accurate, checklist-driven simulation of historical hardware is a credible niche and a good calibration target (sunscatter's own Electron/Falcon-1-first calibration plan rhymes with this). Limits to exceed: single-vehicle, single-era scope, no generic part/type system (each craft is bespoke), and documented numerical/physics bugs in exactly the domain (relative navigation, docking) sunscatter needs to get right by construction.

### Flight of Nova
A hard-sci-fi single-star-system simulator with Newtonian orbital physics, Earth-like atmospheric density profiles, shape-dependent aerodynamic drag, and a modest built content set (3 craft, 16 stations, ~115 missions, one full-scale ~12,700 km planet) ([Steam page](https://store.steampowered.com/app/1069190/Flight_Of_Nova/), [Mudspike thread](https://forums.mudspike.com/t/flight-of-nova-hard-science-space-sim/10792)). What to learn: a small, focused team can deliver a believable single-system Newtonian sim with real atmospheric modelling. Limits to exceed: single star system (sunscatter targets 100-300 ly and real multi-system scope), no part-level subsystem simulation, no thermal/structural fidelity, no time-warp-at-scale concept, small fixed content rather than a generative/compositional part model.

### NASA tools that are game-adjacent (GMAT, Basilisk, 42, Trick)
These are the oracles sunscatter's own adopt-instead-of-build plan already names (scope-2026-11.md section 3.4). **GMAT** and **STK**-class tools are strong at orbit/maneuver/trajectory design but can't simulate complex spacecraft attitude dynamics. **Basilisk** (ISC-licensed, flight-proven, [overview](https://hanspeterschaub.info/PapersPrivate/Kenneally2020a.pdf)) is a modular, Python-friendly, open-source framework with configurable-fidelity coupled orbit/attitude/GN&C dynamics and Monte Carlo support — the closest existing analogue to a "lumped subsystem network with tunable fidelity," and a validation oracle rather than a game. **42** (NASA/Stephen Hughes) is a free, high-fidelity multi-body spacecraft dynamics simulator used for GN&C algorithm development, single-threaded. **Trick** (NASA Open Source, [github.com/nasa/trick](https://github.com/nasa/trick)) is a simulation *framework/scheduler* (not a physics model itself) used to assemble real mission sims (it underlies many NASA training and engineering sims) with deterministic, reproducible scheduling across variable-rate jobs. What to learn: all four separate "the physics model" from "the scheduler/integrator," which is exactly the distinction sunscatter's canonical-grid warp design needs; Trick in particular is a scheduler built for reproducibility across job rates, the same problem as sunscatter's multi-rate co-simulation. Limits to exceed: none of these are games — no rendering, no part/craft editor, no accessible UI, no economy — they validate domains in isolation and were never asked to stay bit-identical across a 5-order-of-magnitude warp range while rendering a live 3D craft.

## 4. Ideas to steal and traps to avoid

### Ideas to steal
1. **Open-sourcing the engine once it's stable grows an ecosystem that outlives the studio.** — Orbiter, and now KSA's BRUTAL.
2. **Make the core game data itself a mod**, so every official content change ships through the same pipeline a modder would use. — KSA.
3. **A true n-body integrator can be bolted onto patched-conics UI** (maneuver nodes, transfer planner) without the player ever seeing the seam. — Principia.
4. **Async, long-horizon trajectory prediction** near complex gravity fields, instead of blocking the sim loop. — Principia.
5. **Build every part/weapon from the textbook formula, not a balance pass.** — Children of a Dead Earth.
6. **Progressive, readable damage**: deform, then lose function, then fail — rather than a single hitpoint cliff. — Space Engineers.
7. **Separate the scheduler from the physics model** so determinism and reproducibility are a property of the scheduler (variable job rates on a fixed grid), not of any one subsystem. — NASA Trick.
8. **Configurable-fidelity, modular subsystem framework usable as both an engineering oracle and a flight-proven architecture reference.** — Basilisk.
9. **Procedure-accurate, checklist-driven flight of real historical hardware** as a calibration/credibility exercise before generalizing. — Reentry.
10. **A single procedural part system spanning multiple vehicle classes (rocket/plane/rover) instead of per-class special-casing.** — Juno: New Origins.

### Traps to avoid
1. **Don't let "spiritual successor" hype outrun the physics that's actually shipped** — claim only what's implemented and tested; KSA's patched-conics-with-no-thermal-or-lift core is well behind its marketing register.
2. **Don't rebuild a new, more ambitious game on an old engine under time pressure** — Take-Two forcing KSP2 onto KSP1's codebase is the direct cause of its failure; this is the same trap as pacing to a deadline.
3. **Don't split the team or the codebase mid-project** — Star Theory/Intercept's split destabilized both halves.
4. **Don't let time-warp be "fast enough to feel right" without a determinism proof** — KSA's warp fps collapse and lack of an invariance claim is the failure mode sunscatter's canonical-grid design exists to prevent.
5. **Don't let docking/relative navigation numerics be an afterthought** — Reentry had to rewrite its rendezvous/docking system after shipping with ~20 cm position jumps; this is exactly the kind of near-field two-body interaction that breaks naive n-body/patched-conics hybrids.
6. **Don't let voxel/terrain damage state become a memory and performance liability** — Space Engineers' voxel carving costs scale with world size and damage history; sunscatter's cell-based structural failure must stay bounded.
7. **Don't hard-cap part count for a mobile target and then try to scale up later** — Juno/SR2's 280-400 part practical ceiling is a design decision baked in early, not a later optimization.
8. **Don't ship a single-vehicle, single-scenario fidelity showcase and mistake it for a generalizable architecture** — Reentry and Flight of Nova are both excellent at their one thing and structurally unable to generalize to new vehicle types without new bespoke code, the exact trap sunscatter's generic-type model is meant to escape.
9. **Don't treat subsystem fidelity (fluids, power, thermal) as separate bolt-on mods layered on an engine that wasn't designed for them** — RO/RSS/Principia's success is real but each is a patch on a 2011 single-rate loop never built for this; retrofitting is harder than designing the lumped-network solver in from day one.
10. **Don't build the scripting/automation API last** — KSA still has no formal scripting framework in pre-alpha; sunscatter's AI-interface parity requirement means automation can't be an afterthought bolted on after the UI is frozen.
